# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Wi-Fi in the TUI's Pair device.** Optional Wi-Fi SSID and password fields under the code: empty for a device on the network, set for a new device found over Bluetooth, which is given the network. The password is masked and never logged.
- `matter.ErrWiFiNetworkRequired`. Without Wi-Fi credentials, `Commission` skips the devices found over BLE, which could join no network, and fails with this error, before connecting, when the device was found over BLE only; with them, it tries the devices found over BLE first.
- **A log in `matterctl tui`.** The menu's **Log** item, or `--log-level info|debug` and `--log-file`, writes the library's log and the TUI's own operations (start, duration, outcome) to `matterctl-YYYYMMDD-HHMMSS.log` in the start directory, with mode 0600. A panel under the others shows its last lines, and `l` shows it full screen. The pairing code is never logged; a debug log holds the decrypted messages, the fabric's IPK included.
- The `MDNSAdvertiser` handles the name conflicts the go-mdns responder now probes for (RFC 6762, 8.1 and 9). On a conflict of the commissionable instance name, it publishes the service with a new random instance name, up to `MaxInstanceNameAttempts` times, and keeps it when the device advertises the same service again; `CommissionableInstanceName` returns the published name. An operational instance name, made of the fabric and the node ID, is not renamed: `AdvertiseOperational` returns an error which wraps the `*mdns.ConflictError`. A host name conflict is an error for both. `HandleConflict` handles a conflict found after a service is published; the advertiser's own responder calls it, and an application which shares its `mdns.Server` with `NewMDNSAdvertiserWithServer` passes it to `mdns.WithServerConflictHandler`.

- **A pluggable storage backend** for the persistent store. `store.KVStore` holds byte values under slash-separated keys and `store.TxKVStore` adds atomic multi-key transactions, which a device will need for the fail-safe. `store.FileKVStore` (one file per key, written atomically, transactions journaled) and `store.MemKVStore` are provided, and `store.NewStoreWithKVStore` builds the typed `Store` on any backend.
- `matter.WithCommissionerStore` passes a `Store` to a `Commissioner` instead of the file store under `~/.{app-name}/`.
- `store.NewMemStore`, an in-memory `Store` for tests, and `Store.DeleteCommissionee`, which forgets a device.
- **A device-side store**, the groundwork for running as a Matter device. `store.DeviceStore` keeps the fabrics a device has joined with their operational credentials, the Access Control entries and the group keys of each fabric, and removes all three together as RemoveFabric does. Its transactions let the changes made while a fail-safe is armed be committed or rolled back as one.
- **The PASE responder**, `pase.Responder`, the device side of PASE. It authenticates a commissioner against a `pase.Verifier` (w0, L, salt and iterations) rather than the passcode itself.
- **`matter/device`**, the start of the device role: a `Device` listens on UDP, answers PASE with its verifier, and hands each new session to the application. `CommissionableService` describes its `_matterc._udp` service (instance name, subtypes and TXT entries), which the default `MDNSAdvertiser` publishes with the go-mdns responder.
- **An Interaction Model server**, `im.Server`, which answers Invoke and Read (with wildcard paths) with registered command handlers and attribute readers. A report must fit in one message.
- `session.WithRole(session.RoleResponder)`, so a device can use a secure session with the responder's keys and session IDs.
- The device serves the Interaction Model on each PASE session with the **General Commissioning cluster**: ArmFailSafe, SetRegulatoryConfig, CommissioningComplete (over CASE only) and its attributes. The fail-safe guards the commissioning changes with a `DeviceStore` transaction, rolled back when it expires. `device.WithDeviceStore` sets the store.
- `credentials.AttestationProvider` and `credentials.Signer`, which a device proves its origin and signs with without exposing its private keys, with `NewAttestationProvider`, `NewSoftwareSigner`, `CreateCSR`, `BuildAttestationElements`, `BuildNOCSRElements` and `SignWithChallenge` for the device side of attestation and CSR.
- `credentials/testcreds`: the public test attestation credentials of the Matter SDK (project-chip/connectedhomeip, Apache License 2.0) for vendor 0xFFF1 and product 0x8000, for development and testing only. The source is given in the README, `NOTICE` and `matter/credentials/testcreds/certs/README.md`.
- The device serves the **Operational Credentials cluster**: AttestationRequest and CertificateChainRequest with the credentials `device.WithAttestationProvider` sets, CSRRequest with a newly generated operational key, AddTrustedRootCertificate, and AddNOC, which checks the NOC and writes the fabric, an Administer ACL entry for CaseAdminSubject and the IPK through the fail-safe's transaction. The NOCs, Fabrics, SupportedFabrics, CommissionedFabrics and TrustedRootCertificates attributes report the fabrics, the one being added included. `device.WithSupportedFabrics` sets how many fabrics the device can join.
- `credentials.ParseOperationalCertificate`, `VerifyRootCertificate` and `VerifyOperationalChain`, which read Matter TLV operational certificates and check a NOC chains to its root.
- **The CASE responder**, `caseprotocol.Responder`, the device side of CASE. It finds the fabric a Sigma1's destination ID names among the device's fabrics, proves the device's identity on it in Sigma2, and checks in Sigma3 that the initiator's NOC chains to that fabric's root. It resumes the sessions it keeps in a `caseprotocol.ResponderResumptionStore` (see below).
- The device answers **CASE** on the fabrics it has joined, the one being added under the fail-safe included, and serves the Interaction Model on CASE sessions, so commissioning completes: CommissioningComplete over CASE on the new fabric commits it. AddNOC binds the PASE session to the new fabric, and rolling the fail-safe back closes the CASE sessions on it. `Session.IsCASE` and `Session.PeerNodeID` describe a session.
- The device advertises an **operational service** (`_matter._tcp`, `<compressed fabric ID>-<node ID>` with the `_I` subtype) for each fabric it is on, from AddNOC on, so a commissioner finds it for CASE; rolling the fail-safe back withdraws it. `device.OperationalService` describes it.
- **The commissioning window.** A device advertises itself as commissionable and accepts PASE only while its window is open: at Start when it is on no fabric (`device.WithCommissioningTimeout`, 15 minutes by default), or after `OpenCommissioningWindow`. A PASE session takes the window: the device stops advertising, arms the fail-safe for 60 seconds and refuses other commissioners. A failed attempt, PASE failing or the fail-safe expiring, advertises again, and the window closes after 20 of them, when it times out, on `CloseCommissioningWindow`, or when CommissioningComplete succeeds, which also ends the PASE sessions.
- `pase.WithResponderEstablishedHandler` and `caseprotocol.WithResponderEstablishedHandler`, which hand the new session over before the initiator is told it is established, so the device has set it up by the time the initiator's first message arrives.
- `mattertest` commissions a `matter/device` Device with go-matter's own Commissioner over real mDNS and UDP, from discovery to CommissioningComplete.
- `mattertest` commissions a `matter/device` Device with **chip-tool** when it is installed (`$CHIP_TOOL` or `chip-tool` on the PATH, such as the chip-tool snap), and reads an attribute over CASE afterwards, logging chip-tool's output. `make test-chip-tool` runs only these tests, and `GO_MATTER_TEST_REQUIRE=chip-tool` fails them instead of skipping when chip-tool is missing. A GitHub Actions job installs Avahi and the chip-tool snap to run them.
- `TestChipToolOpensCommissioningWindow` has chip-tool open an enhanced commissioning window on the commissioned device, and a second chip-tool commissioner join a second fabric through it with the one-time passcode.
- The device handles **RemoveFabric** and **UpdateFabricLabel**. RemoveFabric removes a fabric with its ACL and group keys, and once the NOCResponse is out, closes the sessions on it and withdraws its operational service; a device left on no fabric opens its commissioning window again. UpdateFabricLabel labels the accessing fabric, refusing a label another fabric uses. `im.CommandResult.AfterResponse` runs a command's follow-up once its response is sent. The chip-tool window test also labels and removes the second fabric.
- `credentials.OperationalCertificate.CATs`, the CASE Authenticated Tags of a NOC.
- **Access control in `im.Server`.** `SetAccessChecker` subjects every invoke and read to a check with the privilege its handler requires (`im.WithPrivilege`; Operate for commands and View for attributes by default). A refused command or concrete read is answered with UNSUPPORTED_ACCESS, and a wildcard read leaves the attribute out. `HandleAttributeRead` registers a reader which gets the session and whether the read is fabric-filtered, for fabric-scoped attributes.
- The device enforces its **Access Control List**: a CASE request is granted when an entry of the session's fabric names its subject (node ID, or a CAT of at least the entry's version), the endpoint and cluster, and a privilege which grants the one required; a PASE session, which only exists while the commissioning window is open, is granted Administer. The General and Operational Credentials commands, and reading the NOCs, need Administer. CurrentFabricIndex reports the session's fabric, a fabric-filtered read of NOCs and Fabrics reports only it, and the certificates of other fabrics are left out of NOCs.
- `im.TimedInvoke`, which invokes a command in a timed interaction, as the commands which require one must be.
- `pase.Verifier.Bytes` and `pase.ParseVerifier`, the serialized verifier (w0 followed by L) the Administrator Commissioning cluster carries.
- The device serves the **Administrator Commissioning cluster**: OpenCommissioningWindow opens an enhanced window with the verifier and discriminator an administrator generated, advertised with CM=2, OpenBasicCommissioningWindow one with the device's own passcode, and RevokeCommissioning closes the window and ends a commissioning in progress; the WindowStatus, AdminFabricIndex and AdminVendorId attributes report the window. The commands need Administer and a timed interaction. `Device.OpenEnhancedCommissioningWindow` opens an enhanced window from the application.
- `im.Server` reports the **global attributes** of each cluster from what is registered: AttributeList, AcceptedCommandList, and GeneratedCommandList from the response commands `im.WithResponseCommand` declares. `Server.Endpoints` and `Server.Clusters` list what is registered.
- The device serves the **Descriptor cluster** on the root endpoint, as a Root Node (`device.RootNodeDeviceType`), with its ServerList and PartsList following the registered clusters and endpoints.
- **Writes in `im.Server`.** `HandleAttributeWrite` registers a writer, which gets the value as TLV (`AttributeWriteRequest.Decoder`), whether it appends to a list, and whether the write is timed; it requires Operate unless `im.WithPrivilege` says otherwise. The server answers a WriteRequest with the status of each write: UNSUPPORTED_WRITE for a read-only attribute, UNSUPPORTED_ACCESS for a refused one. The device's Basic Information NodeLabel is writable.
- `pake.Pake1.PA`, `pake.Pake3.CA` and `pake.WithPake2MessagePrecomputed`, which the responder needs.
- `store.PersistentCounter`, a counter that never repeats a value across restarts without persisting every increment, for the boot count and the global group message counters.
- **Device attestation verification** (6.2.3): the commissioner checks that the DAC chains to a trusted PAA through its PAI, that the vendor and product IDs of the DAC, the PAI and the PAA agree, and that the Certification Declaration is signed by a trusted key, covers the vendor and the product of the device's Basic Information, and covers the DAC's vendor and product (or names them as its DAC origin) and its PAA when it lists authorized PAAs. `credentials.AttestationVerifier` runs the procedure in one of three modes: `AttestationDevelopment`, the default, which also trusts the test PAA and test CD signing key of the Matter SDK; `AttestationProduction`, which rejects those test anchors, the test vendor IDs and Certification Declarations for development and test; and `AttestationNone`, which only checks the DAC signature and the nonce. A rejected device fails with a `credentials.AttestationError` naming the failure.
- `credentials/production`, which bundles a snapshot of the Distributed Compliance Ledger's production trust anchors: its 73 approved PAAs and the Certification Declaration signing certificates of the Connectivity Standards Alliance (CSA Certification Declaration Signing Keys 001 to 005), taken from the DCL mirror of the Matter SDK. Every mode but `AttestationNone` trusts them, so certified products are commissioned without further setup.
- `credentials/dcl`, a client of the DCL's REST API which reads the approved PAAs and the CD signing certificates, and `make update-production-certs`, which refreshes the bundled snapshot with it. The `dcl-certs` workflow runs it monthly and opens a pull request when the ledger changed.
- `credentials.AttestationTrustStore`, with `LoadAttestationTrustStore` (a directory of PAA certificates and one of CD signing certificates), `ParseAttestationTrustStore` and `MergeAttestationTrustStores`; `WithAttestationRejectedAnchors`; and `credentials.RevocationChecker` (`WithAttestationRevocationChecker`) for a revocation check.
- `credentials.ParseSignedCertificationDeclaration` and `ParseCertificationDeclaration`, which verify and decode a Certification Declaration, requiring its mandatory fields and format version 1.
- `testcreds.TestCDSigningCertificate`, the Matter SDK's test CD signing key "Matter Test CD Signing Authority".
- `matter.WithCommissionerAttestationMode`, `WithCommissionerAttestationTrustStore` and `WithCommissionerAttestationVerifier`, and `matter.NewAttestationVerifier`, `DefaultAttestationVerifier` and `DevelopmentAttestationTrustStore`. An `AttestationVerifier` can also be passed to `Commission` as a `CommissionOption`.
- **Attribute subscriptions** (8.5): `im.ExchangeMux.Subscribe`, and `Subscribe` of the `matter.AttributeSubscriber` a node from `Commissioner.Connect` implements, subscribe to attribute paths, wildcards included, and call a `ReportHandler` with the priming report and each report after, in order, with chunked reports and list items joined. A subscription answers its reports, takes itself for lost when no report arrives within its max interval and a liveness margin, and subscribes again with a backoff. Options set the intervals, `KeepSubscriptions`, fabric filtering, resubscription and an error handler.
- `im.ExchangeMux`, which reads a session for the exchanges this node initiates and those a peer initiates: responses go to whoever waits for their exchange, with `DefaultResponseTimeout`, and reports to their subscription. A report for an unknown subscription is answered with InvalidSubscription.
- `matterctl any subscribe <cluster-id> <attribute-id|*> <node ID> <endpoint ID>`, which prints the reports until interrupted.
- **CASE session resumption** (4.14.2.2), following connectedhomeip's `CASESession`. `caseprotocol.WithResumption` makes an initiator send the resumption ID and resume MIC of an earlier session in its Sigma1; a responder which still knows the session answers with Sigma2_Resume, which skips the certificates and signatures of a full CASE, and one which does not answers with a full Sigma2. `Initiator.ResumptionState` and `Resumed` tell the state to resume the next session with and how the session was established. `caseprotocol.WithResponderResumptionStore` lets a responder resume the sessions kept in a `ResponderResumptionStore`; `NewResponderResumptionStore` keeps the latest `DefaultResponderResumptions` in memory, one per initiator and fabric. The device keeps one and forgets a fabric's resumptions when the fabric is removed or updated.
- **Commissioner.Connect resumes the last session** with a node it connected to before, in memory only, and falls back to a full CASE when the node no longer knows it. The node it returns implements `matter.Reconnector`: `Reconnect` establishes a new session in place of the current one, through operational discovery, and `Resumed` tells whether the current session was resumed. A request which finds the session failed reconnects first.
- **Subscriptions follow a node to a new session.** `im.WithReconnect` lets a subscription whose session fails, or whose publisher stops answering on it, such as after a restart, subscribe again over the session a `ReconnectFunc` connects instead of ending; the subscriptions of a node from `Commissioner.Connect` set it, and all of them move over when one reconnects the node.
- **A key store for the fabric's private keys** (`matter/keystore`). `matter.WithCommissionerKeyStore` keeps the root CA key and the commissioner's operational key in a `keystore.KeyStore`, under `matter.RootKeyName` and `matter.OperationalKeyName`, instead of in the fabric record. Keys are used through `crypto.Signer`, so a key store can be backed by an HSM over PKCS#11, a cloud KMS or a TPM. `keystore.NewFileKeyStore` keeps one PKCS#8 PEM file per key at `0600`, refusing one others can read, and with `keystore.WithPassphrase` encrypts it with AES-256-GCM under a scrypt key; `keystore.NewStaticKeyStore` serves signers made elsewhere; `keystore.NewMemKeyStore` is for tests. `Start` moves the keys an existing fabric record holds into a key store which can import them, and removes them from the record once it has them.
- `credentials.NewSigner` makes a Matter `Signer` of any P-256 `crypto.Signer`; `credentials.NewCertificateAuthorityWithSigner` issues NOCs with a root key held by one; `credentials.GenerateControllerIdentityWithSigners` creates a fabric identity with keys made beforehand, and `ControllerIdentity` carries `RootSigner` and `Signer`. `config.WithAdministratorSigner` and `config.WithAdministratorRootSigner` set the administrator's keys as signers; CASE signs Sigma3 with the signer and checks that it is the key of the NOC. `credentials.ParsePrivateKey` parses a PKCS#8 or SEC 1 key.
- `matterctl` keeps the fabric's keys in a file key store when `MATTER_CTL_KEY_STORE` names its directory, encrypted with `MATTER_CTL_KEY_STORE_PASSPHRASE` when set; both are read from the environment only. `matterctl tui` creates a new fabric's keys there.
- **Events** (7.14, 10.6.8 to 10.6.10): `im.ReadEvents`, and `ReadEvents` of the `matter.EventReader` a connected node implements, read the events a node keeps of concrete or wildcard `EventRequestPath`s, joining the chunks of the report; `im.WithEvents` subscribes to events too, which reports carry in `Report.Events`. An `EventReport` has the event's path, number, priority, timestamp, with delta timestamps resolved, and data. `WithReadEventMin` and `WithEventMin` filter by event number, and a subscription which subscribes again asks for the events after the last one it reported.
- `matterctl any read-events` and `any subscribe-events`.
- `matterctl pairing --attestation development|production|none`, `--paa-trust-store <dir>` and `--cd-trust-store <dir>`.

### Fixed

- Commissioning a device over BLE could fail at CASE with "no operational addresses found" although the device advertised its operational service with an address: the operational discovery took the first response, which, from a device which has just joined its network, is its commissionable service or its operational service before it has an address. It now takes the last response for the operational service instance with a port and an address, and searches again until one comes.
- Commissioning over BLE failed at once when BlueZ aborted the connection (`le-connection-abort-by-local`), as it does when the discovery's scan has not stopped yet. The connection is now tried up to 4 times, waiting longer each time, as connectedhomeip's Linux BLE layer does.
- `matterctl tui` hid why a pairing failed: it now shows the cause the commissioner returned.
- `Commissioner.Discover`, and so `Commission`, failed on a host without Bluetooth even when mDNS found the device, since a failing BLE scan aborted the discovery. A method which fails is now logged and the other's devices are returned; Discover fails only when both do. This also made `TestMockCommissioning`, and the GitHub Actions build job, fail wherever BlueZ is not running.
- Operational discovery never found a node: `mdns.NewOperationalNodeQuery` for a service instance asked for its PTR records, which an instance does not have, since go-mdns sends the query's own type instead of ANY. It now asks for ANY, and `mdns.Query` carries the question type (`WithQueryType`).
- `pbkdf.NewParamResponse` did not echo the initiator's random when the PBKDF parameters were given, so a responder with its own salt could not answer.
- A PASE initiator that fails to verify cB now sends a failure StatusReport, so the responder ends the exchange instead of waiting for Pake3 until its deadline.
- The commissioner did not check that the AttestationResponse and the CSRResponse echo the nonces of their requests (11.18.7.2, 11.18.7.6). It now rejects a response which does not.
- The CASE initiator accepted any NOC of the fabric from the responder, so a node of the fabric could answer for another. It now checks that the NOC names the node it targeted, and fails with `caseprotocol.ErrUnexpectedResponder` otherwise.

### Changed

- The TUI's Create new fabric reads the vendor ID in hexadecimal, with or without `0x` and surrounding spaces (`FFF1`, `0xFFF1`), and no longer in decimal; the confirmation shows it in both. The TUI logs the inputs its forms reject, without the pairing code or the Wi-Fi password.
- `matterctl tui` is live by default: it opens the commissioner store and operates real devices, each operation still after a confirmation. `--offline` runs the fictional fixture, which was the default, and `--live` is gone.
- `make tui-debug` starts the TUI with its log at debug level, and `.gitignore` leaves the log files out.
- go-logger v1.4.0. The log of `matterctl tui` has millisecond timestamps, and is written to its file and its panel at once through `log.NewWriterLogger`, instead of the panel reading the file back.
- In the forms and dialogs of `matterctl tui`, the action (Validate, Send, Confirm) comes first, with the focus, and Cancel last. The pairing field shows the code as typed instead of masking it.
- `config.AdministratorConfig` has `Signer` and `RootSigner`, which an implementation of its own must add; they return false when the keys are bytes. `store.FabricRecord` omits `rootPrivateKey` and `privateKey` when they are empty, as they are when a key store keeps the keys.
- A node from `Commissioner.Connect` lives until it is closed: its session is read by an `im.ExchangeMux`, which times each response out after `DefaultResponseTimeout`, instead of failing every request once the connect deadline passed. `Node.Session()` returns the mux.
- The session package's helpers, such as `session.PeerMRPParameters`, see through a session wrapper which has `Unwrap() SecureSession`.
- **A commissioner now rejects a device whose attestation does not verify.** Commissioning a device whose PAA is not trusted fails with `AttestationFailurePAANotFound`; add the PAA with `WithCommissionerAttestationTrustStore`, or select `AttestationNone` for a device trusted otherwise. The commissioner reads the VendorID and ProductID of the device's Basic Information during attestation.
- A standalone MRP ack sets the initiator flag exactly when the acknowledged message did not, instead of always; a commissioner's acks are unchanged.
- `device.Session` no longer has `Transport()`: the device serves the Interaction Model on it.
- `device.Session.Keys` returns `session.SessionKeys`, since a session may now be a CASE one.
- `device.Advertiser` has `AdvertiseOperational`, which publishes the operational services, and `WithdrawCommissionable`, which withdraws the commissionable service when the commissioning window closes.
- go-mdns is updated to the version whose responder probes the names of a service before it publishes it, so `MDNSAdvertiser.AdvertiseCommissionable` and `AdvertiseOperational` return after about a second, when the services are published. A shared `mdns.Server` given to `NewMDNSAdvertiserWithServer` must be started before the device publishes.
- A device already on a fabric no longer advertises itself as commissionable at Start, and a commissioned device no longer accepts PASE until its commissioning window is opened again.
- `Store` no longer has a `Dir()` method, since a store which is not backed by a directory has none. `store.FileKVStore.Dir()` still returns it.
- A record is written to a temporary file and renamed into place, so a crash can no longer leave a truncated JSON file. The directory layout is unchanged, and an existing `~/.{app-name}/` directory is read as it is.

## [0.8.0] - 2026-09-23

The first tagged release. go-matter is a commissioner: it commissions a Matter device onto a fabric and operates it afterwards. Running as a Matter device is not implemented, and it is planned for v1.0.0.

### Added

- **Discovery**: a commissionable device is found over BLE and over mDNS, from a manual pairing code or a QR code payload.
- **Commissioning** over BLE (BTP) and over IP: PASE (SPAKE2+), the fail-safe and general commissioning flow, CSR and NOC issuance, and CASE. The whole exchange is bounded by a single deadline, because a device commits its new fabric to persistent storage and re-advertises itself over mDNS before CASE can start.
- **A persistent store** of the fabric and of the commissioned nodes, so that a node is reachable after a restart. `Commissioner.Connect()` reconnects to it with a fresh CASE handshake.
- **The Interaction Model**: Read, Write and Invoke, including the reassembly of a chunked list, over the Message Reliability Protocol.
- **Clusters**, as a client: Basic Information, Descriptor, General Commissioning, General Diagnostics, Network Commissioning, Operational Credentials, Access Control and On/Off.
- **Encoding**: TLV, the Matter message frame format, Base38, the manual pairing code and the QR code payload.
- **`matterctl`**, which scans, commissions and then reads, writes and invokes the clusters of a node from a terminal.

### Known limitations

- The device attestation chain of trust is **not validated**: the exchange runs and its response is parsed, but the certificate chain is accepted without being verified against the Distributed Compliance Ledger.
- There are no Interaction Model subscriptions: an attribute is read on demand.
- Thread commissioning, groups, bindings, scenes, OTA software update and CASE session resumption are not implemented.
- The On/Off cluster and the credentials handling have not been exercised against a wide range of real devices.
